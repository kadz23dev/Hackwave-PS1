================================================================================
1. WHAT HEALTEST IS vs WHAT IT IS NOT
================================================================================
• WHAT IT IS:
  HealTest is an Intent-Aware, Self-Healing End-to-End (E2E) Test Automation and Governance Engine.
  It observes browser UI workflows via Playwright, generates and replays execution step plans, automatically heals broken UI steps when redesigns occur, validates repairs in fresh isolated browser contexts against deterministic backend oracles, and logs tamper-proof audit trails into SQLite.

• WHAT IT IS NOT (STRICT PROHIBITIONS):
  1. DO NOT use TypeScript or compilation tools. Use pure modern JavaScript (Node.js ESM, "type": "module", .js files).
  2. DO NOT use Tailwind CSS, Bootstrap, or any CSS framework. Use pure Vanilla CSS with design tokens.
  3. DO NOT use Express, Fastify, or external web frameworks. Use native Node.js standard libraries (node:http, node:crypto, node:fs, node:path).
  4. DO NOT build a frontend SPA (React, Vue, Next.js). The dashboard is plain HTML5, vanilla CSS, and vanilla JS.
  5. HealTest NEVER modifies the target application's source code. "Fix/Heal" means repairing the TEST AUTOMATION step plan only.
  6. HealTest NEVER uses an LLM to decide test verdicts. Verdicts come EXCLUSIVELY from deterministic backend oracles and network telemetry.

================================================================================
2. CORE PHILOSOPHY & NON-NEGOTIABLE INVARIANTS
================================================================================
Tagline: "Steps may heal. Outcomes may not."

[INVARIANT 1 - DETERMINISTIC VERDICTS (G4/G5)]
- DOM text (e.g., "Order confirmed" on screen) is SUPPORTING-ONLY evidence. It can NEVER pass a test alone.
- If the backend state fails or a 5xx HTTP status occurred on /api/, the verdict is ALWAYS `APP_BUG` (exit code 10), even if the UI showed success.
- Verdict logic (`src/classify/verdict.js`) must have ZERO LLM imports.

[INVARIANT 2 - CONSTRAINED LLM ROLE]
- The LLM is an emergency fallback ONLY (default: off).
- When active, the LLM prompt receives only snapshot element lists and data KEYS (never values).
- The LLM can ONLY output: `{"action": "...", "ref": "...", "dataKey": "..."}`.
- The LLM CANNOT output verdicts, selectors, arbitrary values, or JavaScript code.

[INVARIANT 3 - APPEND-ONLY GOVERNANCE (G7)]
- SQLite tables `audit_log`, `approvals`, `validation_runs`, `oracle_results`, and `step_plans` are APPEND-ONLY.
- Database triggers (`*_no_upd`, `*_no_del`) strictly abort any UPDATE or DELETE operations. Never bypass these triggers.

[INVARIANT 4 - NO FLAKY ASYNC / SLEEPS]
- NEVER use `page.waitForTimeout()` or `setTimeout()` sleeps in Playwright code.
- Always use auto-waiting, locator assertions, or `page.waitForLoadState('networkidle')`.

[INVARIANT 5 - ZERO UNAUTHORIZED DEPENDENCIES]
- Production: `playwright`, `better-sqlite3`, `zod`, `yaml`, `commander`, `@google/genai`
- Dev/Test: `vitest`, `eslint`
- All other networking and system needs must use standard Node.js built-ins (`node:http`, `node:crypto`, `node:path`, `node:fs`).

================================================================================
3. TECHNICAL SPECIFICATIONS & STANDARDS
================================================================================
- Language & Runtime: Node.js (>= 22), pure JavaScript with ES Modules (`"type": "module"` in package.json, `.js` extensions). No build step required!
- Styling: Pure Vanilla CSS using custom properties (`tokens.css`, `app.css`).
- Accessibility API: Use `page.locator('body').ariaSnapshot()`. DO NOT use `page.accessibility` (removed in current Playwright).
- Hashing: Page snapshots are hashed using sha256 excluding bounding boxes and normalizing numeric counts (`Cart (1)` -> `Cart (#)`).
- Traceability: Every unit, integration, and guardrail test title must include its explicit `[R-ID]` tag (e.g., `it('[R-PS-01] loads an intent ...')`).
